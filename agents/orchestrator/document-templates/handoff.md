# Handoff 文件规范

> 人事部优化 v1.1 — 保证任务持续性和连贯性

## 为什么需要 Handoff

团队项目周期长、干扰因素多（Agent 宕机、上下文丢失、人员更替等）。为保证项目在任何异常情况下都能持续推进，每个团队成员在阶段性任务完成后，必须输出 handoff.md 文件。

## 生成时机

每个成员在以下时机必须生成 handoff.md：
1. **阶段性任务完成时**（M1/M2/M3/M4 里程碑交付）
2. **被替换/下线前**（团队调整时）
3. **主动中断时**（遇到阻塞需要他人接手时）

## Handoff 内容模板

```markdown
# Handoff — [角色名] @ [时间]

## 元数据（NEXUS 机制 v2.0 增强）
| 字段 | 值 |
|------|-----|
| From | [角色名]（[部门]） |
| To | [接收角色名] |
| stage | [阶段 code —— 取值见「阶段标注规则」，必填] |
| Task Reference | [任务编号, 来自阶段任务卡] |
| Priority | [Critical / High / Medium / Low] |
| Timestamp | [YYYY-MM-DDTHH:MM:SS] |
| Evidence required | [接收方需要的证据: 测试输出/截图/日志] |

## 当前进度
- 已完成: [列出已完成的工作项]
- 进行中: [列出正在进行的工作项及完成度]
- 待完成: [列出未开始的工作项]

## 关键决策
- 决策1: [说明决策内容和理由]
- 决策2: [说明决策内容和理由]

## 技术细节
- 涉及文件: [文件路径列表]
- 关键代码: [关键代码片段或函数名]
- 配置说明: [环境变量/配置项]

## 待办事项
- [ ] 事项1: [说明及优先级]
- [ ] 事项2: [说明及优先级]

## 注意事项
- [踩坑记录、容易出错的地方]
```

> `stage` 是原「`Phase` [阶段编号]」字段的正名：语义相同，取值受下方规则约束。**历史文档里的 `Phase` 视为 `stage` 的旧名**，不要两个字段并存。

## 阶段标注规则（`stage`）

取值**只允许**来自 Orchestrator 的 10 个阶段 code（权威源 `orchestrator/SKILL.md`）：

| code | 阶段 | code | 阶段 |
|------|------|------|------|
| `0` | 项目预检 | `②` | 分工派活 |
| `0.5` | 需求澄清 | `③` | 并行交付 |
| `0.8` | 可行性判断 | `④` | 任务验收 |
| `①` | 方案设计 | `⑤` | 联调验证 |
| `⑥` | 项目交付 | `⑦` | 报告归档 |

- **只写 code，不写阶段名** —— 阶段名是 code 的展示形态，写进字段就造出了第二份真相。
- **禁止自造阶段名或编号**。项目若要表达更细的粒度，用 `Task Reference` 承载，不要扩 `stage` 的值域。
- **判不出就写 `未标注`，并附一行理由**（例如「本文件同时覆盖 ③ 与 ④，无法归位」）—— 不要猜一个填进去。
- `stage` 表示**这份 handoff 是在什么阶段写的**，不是「项目现在处于哪一阶段」。

## 门（可机器判）

`stage` 只靠人记得填必然漂移。落地时应配一道门，判据至少三条：

1. **值域**：`stage` 不在上表内、且不是 `未标注` ⇒ 拒绝；
2. **码表一致**：门读到的阶段码表与 Orchestrator 的权威码表**逐字相等**，否则拒绝（防两处码表各自漂移）；
3. **第三态**：码表读不到 ⇒ 判「判不了」，**不默认放行、也不默认拒绝**。

`未标注` 是合法值，不是失败；**但它必须带理由**，否则与「忘填」无法区分。

## 存放位置

`~/.gbrain/agent-roles/data/projects/<project-id>/handoff/<role>-<date>.md`

> **阶段不进文件名**：阶段会变、日期不变。把 `<stage>` 写进文件名，会让同一份交接件随阶段推进不断改名（改名即产生第二份真相与孤儿文件），也让「同一角色同一天有多份交接」无法表达。项目若已有自己的 handoff 目录约定可以沿用，但 `stage` 字段要求不变。
